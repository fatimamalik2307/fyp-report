\chapter{Proposed Approach and Methodology}

Zeest uses an integration methodology rather than a new diagnostic algorithm. The method begins with a physician-selected patient and encounter, then prepares consultation notes, inputs and longitudinal history. Existing imaging models, language-model capability and retrieval methods act as supporting components, while the project contribution is the way their outputs connect to patient memory, evidence and physician approval. Chapter~4 defines the workflow for navigation, transcription, input handling, memory retrieval, draft generation, critic review and revision-specific decisions. The methodology applies these requirements through a controlled research procedure in which each stage keeps patient, encounter and source context visible, so a generated draft can be inspected rather than treated as final. Controlled comparisons use a shared case set and recorded configurations so improvements cannot be inferred from architectural complexity alone. Source information remains separate from accepted decisions, and unavailable clinical resources remain explicit dependencies. The evaluation procedure does not supply unmeasured outcomes.

\section{Case Preparation and Input Handling}

The first methodological step is to create a consistent case package for the encounter. The physician opens a patient record, reviews prior encounters and records consultation audio for transcription according to the workflow in Chapter~4. Consultation audio is prepared as structured notes, which the physician can inspect and correct before downstream use. Imaging, laboratory information and medication context remain separate because they have different representations, source formats and analysis needs. Each input must retain its patient identifier, encounter identifier, type, source reference and revision. This prevents stages from mixing old notes with the encounter or treating unsupported input as a finding. The prepared package describes what information is available, where it came from and whether it is ready for analysis. This keeps failed or missing inputs visible of hiding them inside the draft generation process. The package must also distinguish authorised historical sources from inputs captured during the encounter.

\section{Hybrid Memory and Case Organisation}

Hybrid memory connects the encounter to historical context. Relational records preserve patient, encounter, input and approved-decision relationships, while semantic retrieval selects history related to the consultation or question. The Patient Memory Agent returns source-aware context, not a final diagnosis. The Clinical Case Agent then organises corrected notes, retrieved history and specialist inputs into a case representation for reasoning. This package identifies what is current, what is historical, what was retrieved and what is missing. If an input is absent or fails validation, that status is carried forward of creating a placeholder finding. This approach aligns with the database design in Chapter~4, where inputs, drafts, evidence, audit actions and approved decisions are separate records. It supports the comparison with a single-LLM baseline, because the baseline receives less patient-specific structure than the memory and full-system variants. Retrieved observations retain their source revisions and do not become accepted decisions through retrieval alone.

\section{Proposed Agent Processing Pipeline}

Figure~\ref{fig:fatima:method-pipeline} shows the processing pipeline used to coordinate the Zeest workflow. The physician-facing interface produces case inputs, while hybrid memory supplies patient history. The Clinical Case Agent combines those inputs and sends modality-specific information to the Imaging, Laboratory and Medication Safety agents. The Imaging Agent uses a validated pre-trained model only for imaging tasks. The Laboratory Agent analyses supplied laboratory information, and the Medication Safety Agent checks medication context against a resource still to be selected. The Evidence and RAG Agent retrieves external material with source references. The Clinical Reasoning Agent drafts the diagnosis and treatment proposal, and the Safety and Critic Agent checks it before physician review. The pipeline separates data movement from decision authority. Agents may prepare, analyse, retrieve or review information, but they do not record a final clinical decision. The physician sees the generated draft with evidence and critic findings, then approves, modifies or rejects it.

\section{Dataset, Model and Resource Register}

The candidate data and model resources are identified in the reviewed literature. MIMIC-IV supports de-identified longitudinal EHR cases, while MIMIC-CXR and CheXpert support chest radiograph tasks. PubMed or guideline sources may support evidence retrieval, and Synthea can support synthetic patient cases.~\cite{zeestA:mimicIV,zeestB:mimiccxr,zeestB:chexpert,zeestB:synthea} These resources are not interchangeable. Longitudinal memory needs encounter context, while imaging cases must match the selected model's supported labels. Evidence retrieval needs a permitted corpus and citation preservation. Medication review requires a knowledge resource with suitable coverage, and semantic memory requires an embedding model compatible with the vector store. Table~\ref{tab:fatima:dataset-register} records each candidate's role, status and unresolved dependency so final selection is not assumed before implementation. a candidate resource becomes usable only after access, permitted use, preprocessing needs and clinical-domain fit are confirmed. It gives later evaluation work a checklist for deciding which cases and modalities can be included in the ablation study. Resource choices remain documented dependencies.

\section{Data Preprocessing}

Preprocessing depends on the chosen resources, but Zeest's workflow already defines the preparation rules. Patient and encounter identifiers must be de-identified or synthetic. Consultation notes, reports and other text inputs should be structured while remaining linked to their source. Imaging files should follow only the selected model's required input format, because changing image preparation without matching the model can invalidate the finding. Laboratory and medication information should be normalised enough for the agent to interpret it, but missing values should not be invented. Evidence passages should retain source references and retrieval timestamps. Ablation cases should be frozen before comparison so each variant receives the same allowed inputs for its configuration. This prevents a memory-augmented variant or full-system variant from benefiting from accidental case changes. The preprocessing stage supports both system correctness and evaluation fairness. The resulting case definition must remain traceable to its permitted sources throughout preparation, comparison and review.

\section{Evidence Retrieval Method}

The evidence method separates patient-specific context from external clinical knowledge. Patient context comes from the encounter, corrected notes, retrieved history and specialist findings. External knowledge comes from guideline, literature or medical reference material selected for retrieval. The Evidence and RAG Agent forms a query from the selected case context, retrieves candidate passages, filters or ranks them by relevance and returns supporting text with citations. Figure~\ref{fig:fatima:evidence-retrieval} shows this flow. The Clinical Reasoning Agent may use retrieved evidence when drafting a diagnosis and treatment plan, but the evidence must remain visible to the responsible physician. This prevents a black box answer and lets the critic identify unsupported claims, missing evidence or contradictions. The procedure supports traceability because a draft should identify which retrieved passages were used and where they came from. The physician can then judge whether the support fits the patient and whether the draft should be approved, edited or rejected.

\section{Ablation and Evaluation Protocol}

The ablation protocol answers Zeest's evaluation questions. The comparison includes a single LLM baseline, a memory-augmented variant and the full Zeest system. The baseline receives the case prompt only. The memory variant adds retrieved patient history, while the full system adds specialist findings, evidence retrieval and critic review. Figure~\ref{fig:fatima:ablation-protocol} shows how the same case set flows through the variants and into one assessment process. Additional contrasts examine critic and multimodal contribution where the cases support them. The same reference judgement process must be used for every variant. Table~\ref{tab:fatima:experiment-protocol} defines the variants and comparison controls. Outputs should be assessed for case relevance, patient-history use, evidence support, consistency with specialist findings, critic handling and physician reviewability. Metrics, sample counts, rubrics and reviewer roles remain unresolved. Possible measures include agreement with a reference judgement, citation relevance, unsupported-claim count, error categories and physician review effort. Measured outcomes must remain separate from this evaluation procedure.

\section{Dependencies and Open Method Decisions}

The methodology has unresolved dependencies before implementation and evaluation. The clinical domain must match available data, permitted use and a validated model. The transcription component, embedding model, evidence corpus, medication resource and LLM configuration remain to be selected. The LangGraph and Google ADK responsibility split remains a Chapter~6 design decision. Evaluation needs reference judgements, reviewer roles, sample size, rubric and thresholds. These dependencies are important because they determine whether a case can be used, which modalities can be compared and how outputs should be judged. They prevent the design from presenting design assumptions as completed results. The methodology establishes a structured procedure without pretending those choices are complete. The open decisions should be closed before implementation claims or numerical evaluation results are documented with their limitations, and any selected resource should be recorded with its permitted use and limitations. Unselected resources must not be represented as working integration dependencies.

\section{Conclusion}

Zeest's methodology combines case preparation, hybrid memory retrieval, specialist analysis, evidence-grounded drafting, critic review and physician decision control. It supports an R\&D investigation of whether memory, multimodal inputs, agent decomposition, evidence retrieval and critic review improve clinical draft reviewability. The figures and tables define input flow, unresolved resources and ablation comparisons. The procedure keeps the generated output as a draft until the responsible physician approves, modifies or rejects it, preserving the approval boundary established in the functional requirements. Because the prototype is unbuilt, the chapter separates procedure from outcomes. Future work must confirm resources, implement the pipeline, execute comparisons and report measured findings with limitations. This structure gives the team a method for moving from the requirements toward a testable system while avoiding unsupported claims about clinical performance, dataset access or completed integration. It helps later chapters and reviews check whether the integrated design remains consistent with the evaluation.
